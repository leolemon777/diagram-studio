# 系统、企业、云、网络与数据架构

## 先选择视角

- 业务能力：能力与业务域；不强行出现数据库或技术品牌。
- 逻辑架构：模块与职责；技术选择只在用户给出或明确标为建议时使用。
- C4 上下文：目标系统、人员、外部系统。容器视图：可部署/运行的应用与数据存储；此处 container 不专指 Docker。
- 部署：运行环境、实例、副本、网络区域、故障域；不与逻辑模块一一等同。
- 数据：采集、处理、存储、服务、治理，以及每条流的粒度和方向。

官方 C4 对层次的定义参考 https://c4model.com/diagrams ，按任务选择需要的层次，不要求四层全画。

本地已验证的企业应用、三家云、企业分层、ArchiMate 精选子集、Kubernetes 与 C4 组件/动态输入见 [架构模型](architecture-models.md)。

Chen ER、园区/详细网络、机架、Active Directory、网络位置，以及网站/iPhone/Android线框的输入与边界见 [软件与基础设施模型](software-infrastructure.md)。

## 结构模型

每个核心节点有稳定 ID、名称、责任、类型、所属边界。每条边明确 `source → target / 传递什么 / 方向 / 同步或异步`；允许缺失协议，不臆造端口。对仅说明构成的分层图，不编造层间调用。

## 版式配方

- 分层总览：4–6 条横带按读者阅读顺序排；左侧层名，右侧等宽模块。治理/安全等跨层能力放侧栏，说明是横向支撑而非经过它的数据通道。
- C4：目标边界居中，人员/外部系统在外围；边上用动词，节点中写责任。
- 微服务：按业务域分组，入口在一侧，数据在另一侧；消息总线作为异步通道，避免万物双向箭头。
- 云/网络：区域→网络→子网层级，边界线表达隔离；跨区、冗余或管理通路明确标识。
- 数据平台：从数据源到消费场景，批/流通道可并排；数据治理在旁侧。缺少吞吐量等事实时不填写假性能。
- ER：表名、主/外键、字段和基数；多对多需要关联表或注明逻辑模型层级。Chen 与 Crow's Foot 不能混用却无图例。

## 内容优先级

面向领导：业务目标和关键链路占主位，技术选型移入说明。
面向评审：补上边界、协议、异常路径、存储责任和部署约束。
面向实施：不能只交一张总览；接口、数据字典、部署参数另行明确。

## 验收

外部系统是否在边界外；边的方向是否匹配动词；数据库读写方是否明确；候选技术是否标注；同一抽象层次是否一致；是否无意宣称了高可用、安全合规或实时性。
